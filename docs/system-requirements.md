# 読書記録アプリ システム要件書

- 更新日：2026-11-20
- 対象：読書記録アプリ `book-list` のポートフォリオ向け改善
- 関連資料：`docs/screen-design.md`、`README.md`、`migrations/`
- 本書は**目標とするシステム要件**を定義する。現行実装と改修後の仕様は区別し、実装済みの判定は実コード・テストに基づく。

## 1. 目的・対象範囲・資料の分担

ログインユーザーごとに、読書記録を安全に登録・閲覧・更新・削除できるWebアプリを提供する。Cloudflareの無料プランを基本に運用できる既存構成を活用する。

- **本書**：技術構成、認証、データ、機能要件、API、性能、セキュリティ、デプロイ・運用。
- **`screen-design.md`**：ホーム・全件一覧・モーダルの表示項目、レイアウト、画面遷移、操作、状態別の表示、ワイヤーフレームへの対応。
- **`README.md`**：現在動く機能の説明、ローカル起動、設定、マイグレーション、デプロイ手順。実装の進展に応じて更新する。

画面レイアウトやボタンの配置は本書に重複記載しない。画面設計と本書の間で要件の矛盾が見つかった場合は、実装前に整理する。

## 2. 技術構成

| 領域 | 技術・役割 |
| --- | --- |
| フロントエンド | React・TypeScript：ユーザー操作、状態表示、API通信 |
| ビルド／ローカル開発 | Vite・Cloudflare Vite Plugin・Node.js・npm |
| サーバーAPI | Cloudflare Workers：認証、読書記録、写真、集計のAPI |
| データベース | Cloudflare D1：認証関連データ、書籍情報、写真の参照キー |
| オブジェクトストレージ | 非公開 Cloudflare R2：アップロード写真の本体 |
| 認証 | Better Auth：メールアドレス／パスワード、セッション管理 |
| スキーマ変更 | `migrations/` のSQLマイグレーション |

画面 → Workers API → D1／R2 → APIレスポンス → 画面更新、という構成を維持する。外部の書籍検索APIは基本実装範囲に含めない。外部の写真URLは書籍検索機能とは独立して扱う。

## 3. 認証とユーザー分離

- メールアドレスとパスワードでユーザー登録、ログイン、ログアウトできる。
- パスワードを平文保存せず、認証ライブラリが提供する安全なハッシュ処理を使用する。
- セッションを適切に管理し、Cookieを利用する場合は `HttpOnly`・`Secure`・`SameSite` などの属性を環境に応じて設定する。
- 認証が必要なAPIは未ログインの呼び出しを拒否する。
- 読書記録の取得・作成・詳細・更新・削除、画像の取得・更新・削除は、ユーザーIDとレコードの所有者をサーバー側で照合する。
- 他ユーザーのデータを閲覧、編集、削除できない。SQLの値はバインドし、利用者入力をそのままSQLへ結合しない。
- メールアドレスの確認とパスワード再設定は今回の実装範囲外とする。

## 4. 読書記録のデータ要件

### 4.1 記録の項目

- 本のタイトル（`title`）
- 作者名（`author`）
- 読了日（`finished_on`）
- 本の写真：外部URL（`photo_url`）**または**R2キー（`photo_key`）
- メモ（現行のDB定義・Worker実装での実際のカラム名を確認して引き継ぐ）
- レコードID（`id`）、所有ユーザーID（`user_id`）、作成日時（`created_at`）
- 更新日時（`updated_at`）：現行DBには存在しないとの静的調査結果がある。必要に応じて既存データを保持する追加マイグレーションで導入する。

**入力項目は個別にはすべて任意**とする。ただし、書籍レコードの作成・更新後に、タイトル・作者名・読了日・メモのうち**最低1項目に有効な値が存在する**ことを必須とする。空文字や空白文字だけの文字列は有効な値に数えない。写真はこの条件を満たす記録に追加できるが、写真だけの新規登録は許可しない。

### 4.2 写真の一意性

- 写真の登録方式は「写真なし」「画像ファイルをアップロード」「画像URLを入力」の排他的な3方式とする。
- 新規登録時は「写真なし」が初期値。写真が登録された場合、**1レコードにつき有効な写真は1つだけ**とする。
- アップロードはJPEG・PNG・WebP、1枚5MB以下。写真本体は非公開R2に、キーはD1に保存する。
- 外部URL方式は妥当なURLを検証してD1に保存する。外部URLの画像をR2に自動転載しない。
- 写真差し替え時は旧方式の参照を無効にし、不要になったR2写真を適切に削除する。
- 写真のみの削除が可能で、書籍レコード本体は残す。ただし更新後にタイトル・作者名・読了日・メモの有効な値が1つもなくなる更新は許可しない。
- 現行DBにURLとR2キーの双方が登録されたレコードが存在する可能性を考慮し、移行・編集時は意図しない写真消失を防ぐ。

## 5. 機能要件

| ID | 要件 |
| --- | --- |
| F-01 | ユーザー登録、ログイン、ログアウト |
| F-02 | 記録の新規登録（タイトル・作者名・読了日・メモのうち最低1項目の有効値を要求し、写真だけの登録を拒否） |
| F-03 | 登録ユーザー自身の記録の取得・一覧表示 |
| F-04 | 1件の詳細取得（メモ・写真を含む） |
| F-05 | 記録の編集・保存（写真を変更せずに文字項目だけ編集可能） |
| F-06 | 削除確認後の書籍記録削除と関連写真の後処理 |
| F-07 | 写真アップロード、URL指定、差し替え、写真のみ削除 |
| F-08 | 総登録冊数と今年の読了冊数の集計 |
| F-09 | 登録日時の新しい順で、ホーム用の最新5件を取得 |
| F-10 | 全件一覧を1ページ最大20件、ページ番号指定で直接取得 |
| F-11 | 読み込み中・空状態・通信失敗・入力不正・認証失敗・部分失敗を区別して応答 |

画面上の配置、操作文言、表示順・モーダル遷移は `screen-design.md` に定義する。

## 6. API・取得方法の要件

- 現行の `GET /api/books`、`POST /api/books` を可能な限り活かし、機能拡張時に既存フロントエンドへの影響を確認する。
- 詳細・編集・削除に対応する認証付きのAPIを追加する。パスやメソッドの正確な設計は実装時に既存コードと整合させる。
- ホームの最近の記録は**最大5件**を取得する。集計値はD1の集計クエリで求め、冊数算出のために書籍本文の全件を取得しない。
- 「今年の読了数」は**当年の `finished_on` を持つログインユーザーの記録数**とする。日付未入力は含めない。
- 全件一覧は**指定ページの最大20件だけをDBから取得**する。ページは1始まりで、1から任意のページ（例：3）へ直接移動でき、途中のページを順次取得する必要はない。
- 例：`GET /api/books?page=3&limit=20`。対象ユーザーに絞って順序を固定し、検証済みのページからオフセットを計算する。総件数は `COUNT(*)` 等の集計で取得し、表示可能なページ番号を求める。
- 書籍一覧は `created_at` の降順とし、同じ作成日時の場合も `id` などで並び順を安定させる。
- 0冊、ちょうど20冊、21冊、80冊、最後のページを削除した場合、範囲外ページ指定などに対応する。
- APIは非数値・0以下・極端なページ番号、不正なJSON、日付、URL、文字列長、画像形式・容量を検証する。エラー時は利用者が理解できる情報を返す。
- 現在の「書籍作成→写真アップロード」2段階処理では、書籍作成時にタイトル・作者名・読了日・メモの最低1項目を検証し、写真だけの新規登録を拒否する。写真アップロードが失敗した場合、書籍保存状況と写真保存状況を正確に伝え、再試行できるようにする。
- D1とR2をまたぐ更新・削除では、参照切り替えと後片付けの順序、失敗時のリカバリーを設計し、成功していない処理を成功として返さない。

## 7. 非機能要件

### 7.1 セキュリティ

- 認証・ユーザー所有権チェック、適切な入力検証、SQLバインド、環境変数／シークレット管理を徹底する。
- エラー応答や公開の稼働確認API（`/api/health`）で、シークレットや詳細な内部環境情報を不必要に公開しない。
- 写真の非公開R2配信はWorker経由で所有者確認を行う。

### 7.2 性能・可用性

- Cloudflare無料プランの制限内を基本として設計・運用する。
- ホームは最大5件、全件一覧は1ページ最大20件を取得し、画像本体は書籍一覧APIへ埋め込まない。
- 画像がない場合や読み込みエラーには代替表示を用意する。画像の遅延読み込みを検討し、サムネイル生成・圧縮は必要性を測定してから追加する。
- 通信失敗を「記録0件」と取り違えない。再試行できるようにする。

### 7.3 操作性・アクセシビリティ

- PC・スマートフォンで主要機能を操作可能にし、モーダルは画面内に収まるようにする。
- キーボード操作、フォーカス管理、ページ番号の現在位置表示、明確な操作ラベル、削除前確認を提供する。
- 詳細なUI仕様は `screen-design.md` を参照する。

### 7.4 運用

- D1のスキーマ変更をマイグレーションで管理し、本番と開発のデータ・設定を区別する。
- `BETTER_AUTH_SECRET` 等の機密情報はコードやGitに含めない。
- マイグレーション適用前に、既存データと適用履歴を確認する。既存の `0003_books_auth_user.sql` はデータ削除を含むため、安易に再適用・改変しない。
- GitHubへのcommit・push、本番デプロイ、本番DB変更は明示的に指示された場合のみ行う。

## 8. データ構造と実装移行時の確認

既存のBetter Authの認証テーブルを維持し、独自の `users` テーブルを新規に重複作成しない。下記は**書籍の論理データモデル**であり、既存の実スキーマと照合してから変更する。

| 項目 | 必須／任意 | 保管先・補足 |
| --- | --- | --- |
| `id` | 必須 | D1・一意なレコードID |
| `user_id` | 必須 | D1・Better Authのユーザーと紐付け |
| `title` | 任意 | D1 |
| `author` | 任意 | D1 |
| `finished_on` | 任意 | D1 |
| `memo`（論理項目） | 任意 | D1・実カラム名を確認 |
| `photo_url` | 任意 | D1・外部画像URL |
| `photo_key` | 任意 | D1・非公開R2の参照キー |
| `created_at` | 必須 | D1・登録順の基準 |
| `updated_at` | 変更時刻を採用する場合 | 実スキーマに存在しなければ追加マイグレーションで対応 |

`photo_url` と `photo_key` は、新仕様でどちらか一方のみ有効とする。編集・削除導入時は既存レコードの整合性と移行の必要性を検証する。

## 9. ローカル開発・デプロイ

- Node.jsとnpm（または互換ツール）を使用する。
- Vite／Cloudflare Vite PluginとWranglerでローカル実行・ビルドする。
- D1・R2はローカル用または開発環境を使い、本番用シークレット・設定と分離する。
- Cloudflare Workersにデプロイできる状態を維持する。
- 具体的なコマンド、環境変数、注意事項は `README.md` を正とし、本書へ重複掲載しない。

- [ ] 写真なし、R2、URL、写真単独削除、方式切替が整合する。
- [ ] 追加・更新・削除時の部分失敗を適切に扱える。

## 11. 今回の対象外

- 書籍検索外部API連携
- 書名や作者名での検索・任意ソート
- 読書傾向グラフ
- 初期段階での高度なサムネイル生成・画像最適化
- メールアドレス確認・パスワード再設定
